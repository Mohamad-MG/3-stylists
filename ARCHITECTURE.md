# Architecture

## The shape

One public skill routes every request to one of five modes. The Claude Code slash commands are one-line wrappers around that skill, so every host runs the same instructions.

- **audit, polish, enhance, build** share one workflow and need nothing beyond the host's own tools. Their measurements come from one script, the probe.
- **explore** is optional and heavier. It runs pinned third-party design engines through an orchestrator, one isolated stylist per engine, and a gate.

## Map

```

.claude-plugin/  .codex-plugin/  .agents/plugins/
                                 host manifests, generated by scripts/sync-manifests.mjs

skills/altero/
  SKILL.md                       the mode router
  references/workflow.md         audit, polish, enhance, build
  references/bilingual.md        Arabic and English rules, for every mode
  references/arabic-type/        tested Arabic faces and Latin pairs
  references/phone.md            the phone layer, for every mode
  references/explore.md          the Explore orchestrator, with interview.md,
                                 facts-schema.md, engine-inputs.md and gate-checklist.md
  assets/probe.js                measured checks, shared by the standard modes and the Explore gate
  assets/compare.html            the Explore showcase, served by scripts/serve.mjs
agents/stylist.md                one isolated stylist; Explore starts it once per engine
internal/contract.md             Explore: who owns what, precedence, collisions, deliverables
internal/adapters/<id>.md        Explore: how to run one engine
engines/registry.json            pinned engines: repository, commit, licence, role, required paths
scripts/                         engines, env-probe, rtl-edges, fetch-font, ttf2woff2, lib, sync-manifests
test/package.test.mjs            package checks, run with node --test
docs/                            the research behind the engine choices
.github/assets/                  README art: static SVG, display lettering outlined so no font is needed
```

## Rules that keep it maintainable

1. **One place per fact.** Metadata lives in `plugin.json`, engine pins in `engines/registry.json`, the Explore contract in `internal/contract.md`, measured checks in `assets/probe.js`. Every other file points there.
2. **Host files stay thin.** Behaviour lives in the skill, never in a command or a manifest.
3. **The standard modes never depend on Explore's engines.** The package test enforces it.
4. **Explore never restates an engine's design rules.** Adapters say how to feed, run and finish an engine, nothing else.
5. **Every path a document names must exist.** The package test follows every link, `<plugin>/…` and `<refs>/…` path.

## How to change things

| To | Do |
|---|---|
| Release | Set `version` in `plugin.json` → `node scripts/sync-manifests.mjs` → add a `CHANGELOG.md` entry → `node --test` → `claude plugin validate .` → commit and tag `v<version>` |
| Add a mode | A row in the `SKILL.md` table, `commands/<mode>.md`, `MODES` in the test, a row in the README. Put its steps in `workflow.md` or a new reference |
| Add a check | Add it to `assets/probe.js`. Evidence goes in a named group; a pass or fail list goes under `gate`. Name it in `workflow.md` → Measured checks, and in `gate-checklist.md` if Explore must enforce it |
| Bump an engine | Read the upstream changes since the pinned commit → update `commit` (and `sparse`, `entry` or `requiredPaths` if paths moved) in the registry → `node scripts/engines.mjs fetch` and `verify` → re-read the adapter against the new upstream → note it in the changelog |
| Add a stylist | A registry entry with `role.primary: "<id>"` → `internal/adapters/<id>.md` → an input template in `engine-inputs.md` → the variant in `compare.html` and the `run.json` example. The test "every stylist in the registry is wired end to end" names what is missing |
| Add a host | Add its manifest to `hostManifests()` in `scripts/sync-manifests.mjs`. Keep its entry point a thin wrapper around the skill |

## Where things are stored at run time

- Engine and font caches live outside the installed plugin, in `~/.altero/` (`ALTERO_ENGINES`, `ALTERO_GFONTS`), so a plugin update does not fetch them again.
- An Explore run writes to `<project>/.altero/runs/` in the user's project. Nothing is written into the plugin folder.
